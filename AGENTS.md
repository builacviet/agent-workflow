# Project agent rules — entry point

> **CURRENT PROJECT PHASE: DEVELOPMENT (Agent Workflow V1, 2026-11-12).** The repository is actively under manual development and is **not a production-deployed automated agent system**. The local Codex development agent is allowed to run **unit tests / targeted pytest** in its dedicated task worktree and virtual environment to shorten fix–test loops and reduce token/quota waste. The restricted automated **Coder Worker / Code phase** is a separate runtime trust boundary; once deployed it must not execute arbitrary Python/tests on the host. This development-only permission does not waive exact-HEAD GitHub Actions CI or Owner merge gates.

**V1 scope route (Owner-approved, PR #22):** For V1 planning and delivery read [`docs/v1-scope-and-gates.md`](docs/v1-scope-and-gates.md) first. It overrides CL-12/M01 **target implementation choices for V1 only**, not current-as-built evidence, historical ADRs, or security/approval invariants. It does not authorize executing the next task by itself.

**Read before each authorized task:** (1) this file, (2) [`docs/INDEX.md`](docs/INDEX.md), (3) the **currently approved task / acceptance criteria**, then only the relevant code, tests and specific linked document sections. **Do not load all ADRs or the historical handoff log by default.** Distinguish **CURRENT implementation** from **TARGET CL-12 design**; an accepted ADR does not prove implementation, security or production deployment.

## Scope, code and security invariants

- Work only on the Owner/Tech Lead-authorized task and changed-path allowlist. Record exact base SHA, target branch, worktree and head SHA; never edit unrelated projects, credentials, DBs, containers, volumes, tunnels or environments without an explicit task-specific permission. Do not force-push or merge without Owner authorization.
- Target Python 3.11+, type hints, PEP 8, small functions and explicit errors. Preserve order-service `Decimal` rules: finite/nonnegative amounts, never implicit float conversions. Keep `order_service` and the WFC package independently importable; no casual cross-package dependency or unrequested framework rewrite.
- Require deterministic pytest coverage for behavior changes, invalid input and regression. At implementation handoff, run `python -m pytest -q` where possible and record the **actual** environment, command, exit code, skipped count and limitations. Never invent tests, CI checks, Linux security evidence or model effort.
- Use principle of least privilege. **CURRENT Phase 3.1 and approved V1 architecture:** the trusted host Controller invokes the host Docker CLI directly and therefore has broad engine authority; this is an acknowledged, unverified runtime risk, **not** proof of engine isolation. Do not expand generic engine access to MCP, untrusted Codex, Worker or monitoring. The CL-12 typed/authenticated Executor concept is **out of scope and not a dependency for V1**; it is a historical target proposal, not a required V1 security boundary. Do not leak PEM/tokens, GitHub auth, WFC DB or arbitrary host paths into untrusted stages. Avoid unauthorized installs, engine commands, external effects or implicit DB migration.
- **V1 architecture (Owner-approved in PR #22):** reuse the existing **trusted host Controller → Docker CLI** implementation with acknowledged broad engine authority; **do not build a new Executor or migrate to Podman in V1**. Neither technology is a V1 task dependency or an implicit V2 commitment. This never grants untrusted Codex, MCP or monitoring generic engine access or credentials, and does not verify production isolation. See the V1 scope contract for exact precedence.
- Read [`docs/architecture.md`](docs/architecture.md) for **as-built** code; the [CL-12 architecture ADR](docs/adr/CL-12-architecture.md) documents a **historical non-V1 target proposal**, not the approved V1 design. In particular, Linux-host Rootless Podman Executor, GHCR and Grafana are **outside V1**, not required future tasks or evidence of active deployment.

**PostgreSQL coding:** Follow the mandatory [ORM/DTO conventions](docs/conventions/engineering-standards.md#postgresql-orm-and-dto-conventions) for authorized PostgreSQL adapters; Alembic remains schema authority.

## Manual DEVELOPMENT code-quality checklists

- **Manual Codex Dev:** Before opening any Draft PR, follow [Dev implementation & self-review checklist](docs/templates/dev-self-review-checklist.md). **Proactively fix Clean Code defects discovered during self-review within the authorized task scope, then rerun relevant tests**. If remediation requires out-of-scope edits, interface changes or risky refactoring, flag it to Tech Lead/Owner instead; never silently expand scope. Passing tests alone does not mean the code is clean.
- **ChatGPT Tech Lead:** Review each Draft PR using the [TL PR review checklist](docs/templates/tl-review-checklist.md), covering Clean Code, architecture, security, correctness, tests, CI and operations on the exact PR HEAD. Log actionable findings with evidence and proportionate severity.
- Both checklists operationalize [Engineering Quality Standards](docs/conventions/engineering-standards.md). They are **manual DEVELOPMENT** quality practices, not automated TARGET QC/MTP/Planning Package/independent Reviewer gates. Codex self-review never replaces TL review or Owner merge approval.

## Manual local worktrees

- Keep the primary `main` checkout clean and update it only by fast-forward from `origin/main`. Verify `origin`, fetch, and record the `origin/main` SHA before creating a branch. Use and record the exact alternate base only when explicitly approved.
- Use one worktree per task under the primary checkout’s ignored `.worktrees/<task>` on `codex/<task>`. Reuse it only when its branch and base match and its state is clean or explicitly reconciled. Never delete or reset someone else’s worktree.
- Before editing, check `git worktree list` and `git status`, confirm the actual path and branch even in Codex automatic Worktree mode, and read `AGENTS.md` in that worktree. Use disposable test configuration and state. Never copy active databases or credentials.
- **CURRENT DEVELOPMENT phase — manual Codex test permission (Owner-approved, 2026-11-12):** Codex agents working in an authorized local worktree may execute **targeted unit tests and relevant pytest regression tests** using a project-local virtual environment and disposable test data. Prefer narrow test commands first with concise output (e.g. `python -m pytest -q --tb=short tests/test_example.py`); expand to the full suite locally when useful. This permission is for manual development only; it does not authorize production credentials, production/shared databases, privileged Docker/engine commands, network integration tests with external side effects, or unreviewed scripts. **Automated Phase 3.1 Code-stage workers remain unable to execute source/tests directly on the host; the trusted Test stage owns execution.** Local test success never replaces exact-HEAD GitHub Actions CI, architecture gate, independent review, or Owner merge approval.
- At handoff, report the exact worktree path, branch, base and head SHAs, test results, and PR URL. Push the task branch and open a Draft PR when requested. Only the Owner decides whether to merge. See the [local worktree guide](docs/guides/local-worktrees.md) for the Owner’s Windows setup and commands.

## Role, review and handoff contract

- The current **Phase 3.1** POC already runs four Docker-CLI phases (Prepare → Code → Test → Publish) through the trusted host Controller; this is **not** the proposed Linux-host Rootless Podman Executor or authenticated Controller→Executor IPC. See [CURRENT runbook](docs/phase-3.1.md). In the CURRENT automated Phase 3.1 flow, the **Code phase Codex agent only edits the source snapshot**; it cannot commit or push because it receives neither Git metadata nor GitHub credentials. **Trusted Worker Publish** alone commits, ordinary-pushes the task branch and opens/updates a bot Draft PR. Any separately Owner-authorized **manual Coder task** may have its own commit/push handoff contract; do not conflate that with the automated Code phase. **TARGET** changes to job ownership, isolation and IPC require separately approved code/security tests; do not mistake current Docker phases for a deployed Executor.
- **Legacy POC:** ChatGPT Tech Lead reviews code under the existing review policy. **V1 target:** ChatGPT is **TL Planner**; an **independent Codex CLI TL Reviewer** evaluates planning artifacts, code diff and QC results using exact SHA/evidence gates. Maximum **two code-review rounds per task**. Tech Lead-authored docs require independent Owner acceptance, not self-approval. **Only Owner** approves planning packages, merges, next implementation tasks and deployment/cutover.
- For **V1** follow [scope and gate contract](docs/v1-scope-and-gates.md); [review policy](docs/review-policy.md) describes earlier POC review assumptions where they differ. Use the [short task handoff template](docs/templates/handoff.md) when preparing or reviewing a PR. `docs/handoff.md` is a compatibility pointer; old task evidence lives in [history](docs/history/handoff-log.md), read only for audit/comparison.
- The previous Phase 2.2 no-Controller/scheduler scope had a narrowly authorized **Phase 3.1 exception**. Read the actual task and [Phase 3.1 AC](docs/tasks/PHASE-3.1.md) rather than interpreting old prohibitions as a ban on already authorized functionality. No Phase 3.2, production Executor, new CI/registry or Grafana deployment is implied.

**Missing, contradictory or stale context?** Follow the [documentation index](docs/INDEX.md), recheck current source, accepted ADR/PR SHA and active Owner decision; report uncertainty rather than guessing or expanding the task.
