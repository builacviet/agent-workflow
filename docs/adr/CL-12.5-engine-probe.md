## Documentation-backed comparison, not experimental proof

Official documentation was consulted on 2026-11-06. The following design
inferences require the matrix above before selection.

| Dimension | A: host-service rootless Podman | B: dedicated rootless Docker |
| --- | --- | --- |
| Operation model | Local CLI can manage containers without an API service; executor service still needs lifecycle, local user environment and authenticated IPC | Persistent daemon adds user-service/socket/storage lifecycle; executor alone receives its dedicated endpoint |
| Privilege | Dedicated unprivileged account limits root authority, but arbitrary commands/mounts still expose that user's files and engine resources | Rootless daemon and containers use user namespaces; dedicated identity and rootless proof still mandatory, not interchangeable with userns-remap or Desktop |
| API boundary | Avoid exporting Podman's general API by using local CLI in trusted host service; daemonless is not an isolation certificate | Dedicated rootless socket is broad authority inside its user scope; a generic create proxy must not become Controller's job API |
| Resource policy | Need actual cgroup delegation and negative enforcement tests on selected version | cgroup v2/systemd and CPU/memory/pids delegation are prerequisites for cgroup limit enforcement; absent setup can make flags ineffective |
| Integration cost | Linux host-service deployment and user lifecycle are additional operations outside Compose; Docker-like syntax is only a starting point | Existing Docker-oriented adapter gives a compatibility hypothesis, but moving to a dedicated rootless endpoint still changes path/UID/network/cleanup assumptions |
| Windows | Podman Machine introduces VM/user path translation and separate tooling/cache; cannot infer native Linux parity | Docker Desktop is available here but does not satisfy B's dedicated rootless proof; a separate Linux VM setup is still needed |
| Secret/network controls | Neither rootless nor daemonless inherently provides stage egress allowlists or secret segregation | Same requirement: typed policy, isolated mounts, constrained egress and no-network test stage outside generic engine API |

Podman describes its local CLI as daemonless and usable by regular users; this
supports considering a host Executor, not approving it. See
[Podman overview](https://docs.podman.io/en/latest/markdown/podman.1.html).
Its general API grants full functionality and code execution as the API user;
authentication does not convert it into a per-job allowlist. See
[Podman service security](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html#security).
Podman Machine is VM-based on Windows, with WSL/Hyper-V provider choices. See
[Podman Machine](https://docs.podman.io/en/latest/markdown/podman-machine.1.html).

Docker distinguishes genuinely rootless daemon execution from userns-remap and
requires subordinate IDs/mapping utilities. See
[Docker rootless mode](https://docs.docker.com/engine/security/rootless/).
Resource limits require suitable delegation; privileged rootless-DinD recipes
are excluded by this task regardless of convenience. See
[Docker rootless tips](https://docs.docker.com/engine/security/rootless/tips/).
No installation, context-switch, service-enable or privilege-changing instructions
from these pages were executed. These are documented capabilities, not measured
security differences on this host.

or implement Executor from this evidence.** A host Podman CLI Executor merits
an isolated first feasibility test because it avoids needing a general Podman
API inside a container, but that is a packaging/security hypothesis, not a
preference established by passing tests. B remains viable if it produces stronger
compatibility/enforcement/operability evidence. Do not fall back to rootful
execution when either rootless candidate is blocked.

Inside that sandbox, approved installation/provisioning of rootless Podman and rootless Docker plus mapping/network/storage prerequisites as needed; separate unprivileged service users, subordinate ID ranges and cgroup v2/systemd delegation. 4. A disposable test-only Executor/Controller IPC harness with fake auth, private bounded job API and sandbox-only workspace/state, not a production source change. Approve local authenticated transport and policy checks; no engine API over TCP, no engine socket in Controller/MCP/Codex, no privileged/host-network/host-PID/unconfined fallback.
5. Later, a separately approved dedicated Podman Machine/rootless Linux VM development parity test if desired; any installation/VM/download/context collision must be reviewed first. No default context/connection or system PATH changes.
