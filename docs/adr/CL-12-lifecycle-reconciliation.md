## 2. Authority and truth sources (candidate TARGET contract)

| Authority | Owns | Cannot authoritatively establish alone |
| --- | --- | --- |
| Owner | Approval of task scope, role/branch policies, exceptional recovery disposition, merge and cutover | GitHub remote state or engine settlement without evidence |
| WFC domain + local transaction store | Task authorization, manual/automated mode, exact-SHA handoff/review, immutable verdict history and two rounds | Current remote GitHub ref, PR or running container |
| Dispatch lifecycle store / Controller | Admission, durable job/dispatch/round fence, stage intent and local finalization | Host engine/container ownership or remote publish success by itself |
| Dedicated trusted Executor (TARGET) | Versioned stage policy, immutable engine identity/owned lifecycle, verified stage state/artifacts; typed status/stop/reconcile evidence | Approval of PR, third review round, invented GitHub success |
| Trusted Worker Publish + independent read-only verifier | Intended commit, ordinary Git push, Draft PR mutation and checked GitHub ref/PR receipt | Local DB commit/review status after process failure |
| GitHub | Actual branch ref, commit ancestry, PR head/base/repositories/draft/actor/body | Whether WFC task or local dispatch was finalized |

**No distributed ACID transaction is claimed across SQLite, engine and GitHub.** Success must be derived from durable local intent plus **independent evidence** of each external effect. Failures with ambiguous outcomes stay fenced and require explicit operator reconciliation; a timeout or process exit is not rollback evidence.

**Split-ledger reconciliation rule (proposal).** WFC + dispatch must use **one independently verified, currently opened physical SQLite database and transaction authority**; matching path strings are insufficient. Only that transaction authority may grant admission and automated review eligibility. A separate durable Executor journal owns engine command/handle/settlement records and is queried over authenticated typed IPC, never written directly by Controller. Correlate both with immutable environment/DB-generation, job ID, dispatch ID, stage attempt and policy digest. Neither ledger may overwrite the other's history when observations differ. Controller's cached state or an Executor `DONE` alone cannot release a slot or grant review. On mismatched journal, restart, restore, generation change or missing intent, **stop admissions, retain/restore a conservative fence, verify engine and GitHub effects independently and escalate**. A DB restore can discard local intent while remote effects survive; restoring an older DB does not prove cancellation. Exact DB generation/restore policy and durable external reconciliation registry are gated by **D-02A** in this M01 decision register; CL-12.4/CL-11 data migration and operational restore remain separately approved downstream decisions, not an undefined M01 D-04 or live restore authorization.

## 3. Stable identity, durable writes and invariants (TARGET proposal)

### 3.1 Identity binding, per-stage journaling and proof of settlement

Define an immutable, operator-authorized **job identity** tied to: `task_id`, exact `round_number`, `input_sha`, `dispatch_id`, authorized repository/branch/base, environment and **physical DB generation**, approved workspace ID, policy version and image manifest digest. Each stage attempt additionally binds stage enum (Prepare, Code, Test, Publish), unique attempt ID, request digest, engine namespace/endpoint identity and trusted artifact reference. Persist this correlation in the Controller/dispatch ledger and Executor's independent journal with an authenticated identity-bound request; schema and transport await separately approved CL-11/T02 decisions.

**Each of the four stages must satisfy this ordered write/effect contract, not only the final stage:**

1. **CREATE_INTENT durably journaled by Executor** with attempt, approved engine namespace, immutable launch policy, container-create identity request and deadline **before** issuing create. Controller records the authorized stage/request intent before submitting; an uncertain IPC submit keeps the Controller fence.
2. **CREATE outcome:** if accepted, store the exact immutable engine/container ID and matched creation evidence in Executor journal **before issuing START**. If response is lost or journal commit fails after engine acceptance, classify `UNKNOWN_CREATE`; reconcile authoritative engine events/owned ID under the verified namespace. A guessed name, temporary absence, another process exit or late timeout can never settle the create. No automatic second create.
3. **START_INTENT durably journaled** against that persisted exact handle **before START**, then confirm/persist engine start acceptance or `UNKNOWN_START`. Lost start response does not authorize repeat or start of the next stage.
4. **RUN/EXIT and outputs:** persist engine-observed terminal result and trusted bounded artifact evidence; record a distinct `STOP_INTENT` if cancellation/termination is requested. Persist stop request before any stop command. Reconcile lost stop response against **the exact immutable instance**, including engine lifecycle events. `CLIENT_EXITED` is not container settlement.
5. **REAP_INTENT and settlement:** persist removal intent, validate owned engine/handle against the journal, reap **only the verified immutable instance**, confirm terminal/non-running and absence with authoritative engine evidence, then durably record `STAGE_SETTLED`. If a create/start/stop/reap command may still arrive late, or engine journal/namespace differs, retain `UNKNOWN_*` and the dispatch fence. A single negative container listing cannot prove no future effect. **Owner approval alone never permits quarantine, release or reassignment**: terminal authenticated engine/Executor records must prove that every prior create/start/stop/reap operation is conclusively rejected or terminated **and can no longer arrive or act** in the relevant engine namespace; additionally, enforceable namespace/handle/generation isolation must prevent any stale operation from touching a replacement container or reassigned resource. A proposed quarantine may be used only as **continued isolation with the slot fenced**, unless this technical non-effect proof is demonstrated and the verified operator disposition is committed. After restart or DB restore, missing or unprovable command history is UNKNOWN and remains fenced, with no time-based shortcut. **Next stage may start only after previous stage is settled**, its artifacts verified, and its auth/credential disposition passes the stage gate. Persist stage-specific completion independently, not only job-level status.

Executor is the **only** proposed owner of engine command journal and immutable handles; Controller receives typed attested status and independently correlates its own dispatch record. Exactly how a crash between effect acceptance and journal persistence can be reconciled (engine event/log retention, authenticated reconciliation owner, late-command quiescence) is an **unresolved acceptance requirement**, not evidence currently available. If settlement cannot be proven, the safe state remains blocked rather than fabricating an ID or declaring no effect.

The CURRENT `docker run` attached process and derived-name cleanup do **not** implement this TARGET create/start/reap contract.

### 3.2 Safety invariants (I01–I12)

1. **I01 — Idempotent admission.** Same authorized job+payload gets its previously durable status; changed payload with same identity is rejected. Same task/round/input key never silently becomes a new job after ACK; no automatic same-key replay.
2. **I02 — One active authoritative assignment.** A task/round/input has at most one active automated dispatch. An overlapping manual handoff is fenced, except via explicit Owner-approved override with settled effects.
3. **I03 — Durable intent before effect.** Each stage's create, start, stop and reap requires its own operation/attempt intent committed by trusted Executor **before** the external engine action. Each separate push, PR POST and PATCH requires its own committed mutation intent. A failed or unknown persistence outcome prohibits further effects.
4. **I04 — Owned-only cleanup.** Validate physical DB, engine namespace and immutable owned handle against durable intent **before any destructive action**. If identity or delayed-create status is unknown, never delete or release based on name/label alone.
5. **I05 — Immutable tested artifact.** Trusted manifest binds approved path/type/mode/bytes and trusted Test policy/result to the exact artifact considered for Publish. No Publish if changed or unverified; details belong to M10/M11.
6. **I06 — Publish authorization fence.** For **each** push, PR POST and PR PATCH, the trusted publication authority MUST **atomically check** the current task/branch writer lease and generation, exact task/round/input/dispatch, scope/deadline and previous outstanding operations **and durably reserve that specific operation's unique ID/intent in the same SQLite writer transaction before allowing the send**. This operation-scoped send reservation fences the branch and survives process pause, lost response, lease expiry, Controller restart and Owner override—even if Worker was suspended **after the check but before any network send**. Neither lease timeout nor re-check alone revokes a previously reserved sender. A conflicting writer may acquire branch authority only after trusted evidence proves the old reservation ended without external effect or all remote effects were settled **and** the old sender/credentials can no longer issue a late operation. Otherwise preserve the writer fence and block new publish. Revalidate expected ref/PR under an Owner-approved enforceable branch policy (read-before-write is not atomic GitHub CAS).
7. **I07 — Remote truth.** Worker HTTP/push response, exit status or `result.json` alone does **not** establish successful Publish. Independently re-query exact GitHub ref, PR head/base repositories, draft/actor and evidence body against intended commit/branch/policy.
8. **I08 — Unknown stays blocked.** Lost create/start/stop/reap/push/PR response, conflicting ref, unresolved stage or unverifiable artifacts never trigger automatic destructive cleanup, duplicate publish, handoff repair or review eligibility. **Unknown credential grant/revoke is a separate security gate:** independently verified GitHub publication may remain `PUBLISH_VERIFIED`, but automated finalization, review eligibility **and slot release stay blocked** until technical evidence establishes **no residual effective write capability**: independently verified token revocation, proved expiration after a conservative clock margin **and** no surviving alternative grants, or verified enforceable containment that actually denies the specific grant's remaining writes. **Owner authorization chooses the disposition but never substitutes for this proof.** Unknown or merely asserted containment remains fenced. Worker result, revoked flag or missing token cache are insufficient.
9. **I09 — Local atomic completion.** Automated `dispatch DONE`/slot release and WFC `READY_IN_REVIEW` handoff must commit in one compare-and-set **SQLite transaction over the same verified physical DB**, binding exact dispatch/round/input, immutable finalization ID, verified remote receipt, all settled stages **and resolved credential disposition**. A provisional handoff, if designed, is not reviewable. If commit acknowledgement is lost, re-read immutable finalization/event history by ID in the correct DB generation; do not repeat write or infer failure from stale status (review or next dispatch may have progressed).
10. **I10 — Manual/automated isolation.** Manual handoff follows its own authorized contract; it cannot silently replace an active automated job or consume a correction round. Historical already-progressed reviews are preserved during reconciliation.
11. **I11 — Review governance.** Exact-SHA claim, durable review/finding history, two-round maximum, independent remote freshness check and Owner-only merge are preserved. Executor and Worker cannot approve reviews.
12. **I12 — Auditable operator reconciliation.** Every authorized release/override records authenticated operator identity, immutable evidence references, outcome classification, affected DB-generation/job/engine/remote identifiers, consent/scope and timestamp. Slot release must be a conditional transaction on the **exact still-held dispatch** that also records the disposition; a changed/missing owner or unknown stage/token/remote truth means no release. No evidence of completed remote effects, exhausted late engine commands and disabled write credentials/senders → no release.

### 3.3 TARGET state model (logical names, NOT existing DB schema)

Per stage, repeat **`CREATE_INTENT → CREATED_HANDLE_PERSISTED → START_INTENT → RUNNING → EXIT_EVIDENCE → STOP/REAP_INTENT → STAGE_SETTLED`**. An already naturally exited stage still requires verified reap and settlement; a cancellation adds `STOP_INTENT` before engine effect. Any commit/effect discrepancy enters `UNKNOWN_CREATE/START/STOP/REAP`; keep the fence. Each stage must settle **before** advancing to the next, including the last Publish stage.

At the dispatch level: `AUTHORIZED → CLAIMED → PREPARE_SETTLED → CODE_SETTLED → TEST_SETTLED → PUBLISH_INTENT → PUBLISH_STAGE_SETTLED → PUBLISH_VERIFIED → CREDENTIALS_SETTLED → LOCAL_FINALIZED(DONE + READY_IN_REVIEW)`. **Only `PUBLISH_VERIFIED` may follow the success path**. `REMOTE_PARTIAL` and `PUBLISH_UNCERTAIN` are **blocked terminal-for-now investigation branches**, not transitions to `CREDENTIALS_SETTLED` or `LOCAL_FINALIZED`; they retain the dispatch and writer fences until authoritative reconciliation. Any earlier operation-scoped send reservation remains fenced until its late-effect window is demonstrably closed. A Publish-stage container may finish before remote verification completes; remote classification is a **separate read-only trust gate**, not inferred from the stage's exit. None of the stage-settled markers can be skipped. A verified remote branch advance with missing/stale Draft PR is **REMOTE_PARTIAL**, not successful publish or verified no-effect. On UNKNOWN, preserve the global exclusion fence. A separately authorized operator disposition may release an exact still-held slot only with proved stage/engine late-effect exhaustion, remote operation settlement, credential write-capability elimination and absence of stale authorized senders; **quarantine without these proofs only retains isolation and the fence**. The original input key stays spent. No normal retry may invent a newer job ID for the same uncertain side effects.

Current `ACTIVE/BLOCKED/DONE/ACKNOWLEDGED` ledger states and WFC review statuses are **not** the proposed stage states. `CLIENT_EXITED`, `STOP_REQUESTED` or an empty engine query is insufficient proof of `STAGE_SETTLED`.

## 4. Durable checkpoint ordering and irreversible-effects policy (TARGET proposal)

The table applies to **each** of Prepare, Code, Test and Publish. Each write-before-effect is an **atomic durability requirement in its own authoritative journal**, not an in-memory flag. A caller timeout or lost response can occur on either side of every commit/effect boundary. Do not hold an SQLite transaction open across engine or GitHub network calls.

| Order | Must be durable **before** effect | Effect / post-effect authoritative evidence | Lost response or conflicting records |
| --- | --- | --- | --- |
| A — Admission | Same physical WFC/dispatch SQLite transaction atomically checks task/round/input/manual-vs-auto ownership and writes exclusive claim/fence | Read the assigned job, DB-generation and fence on the writer connection | No stage request; re-read task and dispatch by ID, do not create a replacement |
| B1 — Per-stage CREATE | Controller authorized request persisted; Executor persists stage+attempt+engine/policy **CREATE_INTENT** before engine create | Engine-created immutable ID + namespace and matching event stored in Executor journal | `UNKNOWN_CREATE`; no relaunch, no negative-listing shortcut |
| B2 — Per-stage START | **Created exact handle must already be durable**; persist separate `START_INTENT` before start | Engine start result/event for same ID and attempt, durably stored | `UNKNOWN_START`; no repeat start/advance |
| B3 — Per-stage EXIT/STOP/REAP | Host-owned artifact/exit evidence; distinct `STOP_INTENT` before stop and `REAP_INTENT` before removal | Verify same immutable ID, terminal status, no outstanding late create/start/stop, bounded artifacts and persisted `STAGE_SETTLED` | Hold fence; no next stage (including Code after Prepare, Test after Code, Publish after Test) |
| C — Protected artifacts/Test | Trusted tested path/type/mode/bytes manifest + test selection/exit provenance under stage identity | Publish must read and verify *same* sealed tested artifact; tests/credentials gates separate | No publish; missing/stale evidence is blocked, never inferred from exit 0 |
| D — Publish authorization | **Same writer transaction:** validate active task/branch lease+generation, task/round/input/dispatch, tested artifact, scoped deadline and lack of conflicting operations; **persist unique operation-specific SEND_RESERVED intent before releasing the sender** | The trusted sender consumes only its exact durable operation authorization; check expected remote ref/PR at send, with enforceable single-writer branch policy | If old Worker pauses before send, reservation STILL fences branch; timeout/override cannot transfer writer authority until old sender/credential is demonstrably unable to send late |
| E — Git PUSH | **PUSH_INTENT/SEND_RESERVED** is created **in D's lease-check transaction** with operation ID, expected old ref, intended new SHA/parent, branch, tested artifact and writer generation | Independently read exact remote ref, ancestry and operation receipt; terminal command and sender quiescence must also be established before ending reservation | `PUSH_UNKNOWN` / partial remote result; do not repeat or transfer branch ownership merely because client returned or deadline passed |
| F1 — Draft PR POST | **POST_INTENT/SEND_RESERVED** written **atomically with a fresh lease-check** as in D; operation ID, expected existing-PR=none, head/base repo+ref, draft state and evidence digest | Independent PR search: exact repo/head/base, open/draft, creator, ID, body/evidence and remote ref; verify mutation settled and old sender disabled before clearing reservation | `PR_UNKNOWN`; no duplicate POST, no branch lease transfer on unproven response loss |
| F2 — Draft PR PATCH | **PATCH_INTENT/SEND_RESERVED** written **atomically with a fresh lease-check** as in D; operation ID, exact stable PR ID + expected head/base/draft/body/actor conditions | Independent GET of **same PR ID**, ref/head/base/repositories/draft/author and expected evidence digest; separate trusted API grant/audit for who performed PATCH; prove sender quiescence before releasing authorization | `PR_UNKNOWN`; creator of an existing PR does **not** prove PATCH principal; no repeated PATCH or branch transfer |
| G — Credentials | Durable request/timestamp/scope/expiry reference before grant where policy allows; record each minted grant identity in trusted custody without plaintext | Independently prove **effective write grants are gone** by confirmed revoke, expiry with clock margin and no residual grant, or tested deny-all containment against the specific write principal; audit the evidence | `CREDENTIAL_UNKNOWN`: remote verified publication remains separate; **no DONE, READY or slot release** on Owner approval alone without technical non-write proof |
| H — Local finalization | All stage settlement records, protected test artifact, accepted exact remote receipt, resolved credential disposition and unique **finalization ID** | **One** `BEGIN IMMEDIATE` local transaction rechecks exact DB-generation/task/round/input/dispatch and commits verified receipt, `DONE`/slot release and WFC `HANDOFF`/review eligibility together | On lost commit response, **read by finalization ID + immutable event/history**, not a retry based on task status; don't reset already-progressed review or a later slot |

**Remote write fence across time:** The lease check and per-operation send authorization must be **one durable local transaction**; the authorized operation ID keeps the writer fence even if the worker is paused before the send or a request is later in flight. A check immediately before push/POST/PATCH does not prevent a network request already in flight from committing after a deadline, override or connection loss. Therefore task/branch writer authorization may not be reassigned while a previous **reserved, unsent, sent or uncertain** mutation exists, unless a protocol proves both (a) any prior external effect is resolved and (b) the old sender cannot issue a delayed mutation under any surviving grant. Owner approval is necessary for a recovery policy but not sufficient technical proof. Effective branch protection/writer exclusivity must be verified outside source. Ordinary Git push is kept; read-before-write is not GitHub compare-and-swap and a later read does not identify the PATCH caller. Before assigning a conflicting writer, prove old effects settled or retain the fence.

**Partial publish:** A correct branch SHA with no PR, a PR with old body or an inconsistent head is `REMOTE_PARTIAL`, not `PUBLISH_VERIFIED`. A remote receipt needs durable intended operation ID, commit/parent, branch policy, exact ref plus PR ID/head/base repositories and refs/open/draft/author/body/evidence and trusted actor evidence. The independent read only establishes observed state at that instant and does **not** prove there are no still-in-flight late mutations. The separate Tech Lead review/merge-time remote-freshness check remains mandatory.

**Verified no-effect is a high bar:** Not merely `git push` returned error, no PR found, old ref observed once or local child terminated. Require proof the request was never sent **or** an authoritative terminal rejection plus settled command/network lifecycle and no outstanding late mutation, together with consistent remote state/history. If this cannot be established, record UNKNOWN and keep the fence.

**Revoke policy (conservative default, D-03C NOT APPROVED):** A Worker `result.json`, success code or client response **cannot independently prove publication**; only the independently read, matching GitHub ref + PR receipt qualifies for `PUBLISH_VERIFIED`. That verified remote result is **separate** from credential safety. Before `DONE`, review eligibility or slot release, require technical evidence of independently verified revoke; or independently confirmed expiry (with conservative clock margin) plus proof no surviving alternate write grant; or **effective, validated containment** that blocks writes by the actual principal/token (not simply a configured rule or claimed deletion). Owner may approve which verified technical disposition is acceptable, but **Owner approval without the technical non-write evidence never opens the gate**. A missing token cache, cancelled client, killed container or an unverified revoke response is insufficient. If any authorized sender can still send a delayed mutation, retain both writer and dispatch fences.

**Stage cleanup before finalization:** A settled Publish stage, like every prior stage, requires exact owned stop/reap evidence. No final cleanup outcome is inferred from the final worker exit or from a task already in `READY_IN_REVIEW`.

## 5. Manual versus automated admission, atomic review eligibility and commit-unknown (TARGET proposal)

**One common arbitration point (D-02C).** Manual `register_task_handoff`, automated `DispatchLedger.claim` and automated local finalization must use the **same verified physical SQLite DB and serialized writer transaction (`BEGIN IMMEDIATE` or proved equivalent)**. Admission reads task status, round, input SHA, explicit manual/automated assignment mode, active dispatch/unknown effects and authorization **inside the same transaction that writes the claim/fence**. Manual intake must read/check that *same* fence, mode, round, input and actor **inside its own write transaction** and atomically commit handoff/event or reject. A preflight check outside the transaction is informational and never sufficient.

- **Manual wins first:** a committed authorized manual handoff makes the prior task/round/input ineligible for later automated claim. Controller cannot claim based on a stale queue snapshot.
- **Automated wins first:** the committed auto fence makes any competing manual handoff fail **without any WFC state mutation** while automation or its side effects are unsettled. An Owner override needs separate durable evidence that old operations (including in-flight GitHub writes) have been settled, not merely a timeout or job cancellation.
- **During Publish:** even if override or deadline changes, the system must *not* declare exclusive branch authority transferred until every reserved/unsent/sent push/POST/PATCH operation is demonstrably settled and the stale sender's write capability disabled; an Owner-approved quarantine with unresolved late effects keeps the writer fence and cannot transfer authority; finalizer fails closed if authorization was lost. Do not permit old job to consume a new review round.
- **Automated completion:** only the trusted finalizer, never a Worker tool argument, writes receipt + local terminal dispatch state + WFC `READY_IN_REVIEW`/`HANDOFF` atomically under a unique immutable finalization ID, after all stage/remote/token gates. Compare exact task, round, input, dispatch holder and DB generation. A provisional handoff, if later approved, is explicitly **nonreviewable**.
- **Lost commit response:** the finalizer/Controller must independently re-open the same physical DB and query immutable finalization record/dispatch/event history by **finalization ID**, not rely only on current task status. The task may have progressed to `IN_REVIEW`, recorded a verdict or released the slot to a different dispatch. An already committed finalization is a *read-only idempotent result*; a missing/unverifiable record is UNKNOWN, not permission to write again.
- **Restore/disagreement:** if physical DB generation changed or Executor still reports an old pending stage absent in the restored DB, block admission and review activation until the old attempt/remote effects are reconciled under D-02. Never reconstruct a terminal event or reset a historical verdict on an unaudited restore.
- **Historical CURRENT split:** a previously valid handoff may already have a claim/verdict while its dispatch remains `ACTIVE/BLOCKED`. Preserve its immutable exact-SHA event/history and classify the orphan slot separately. This proposed new finalizer must not replay the handoff or overwrite progressed review state.

This specification does not prescribe code changes to the existing manual flow until the Owner resolves actor and role separation under **D-02C** in this M01 register (with downstream role/effort policy still separately gated) and authorizes M07 implementation.

## 6. Operator-only reconciliation matrix (TARGET proposal)

For every row, first verify **physical DB + generation, identity of the exact slot holder, engine namespace, durable owned container handles, stage settlement, remote ref/PR, and credential disposition**. Persist authenticated operator, evidence references and explicit category. An operator may issue owned stop/reap **only** after immutable ownership is verified; a cleanup action is distinct from slot release. To release, perform a conditional SQLite transaction on the same **still-held** dispatch that atomically records the disposition and frees the slot; if the holder/generation changed, do not release. This is a **proposed future policy**; CURRENT CLI lacks these checks.
