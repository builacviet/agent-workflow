## Eight architecture decisions — preferred baseline, pending validation

| ID | Decision | Selected baseline and guardrails |
| --- | --- | --- |
| ADR-01 | Deployment model | Modular Monolith in one monorepo, with independent `mcp` and `controller` Docker Compose services sharing a pure workflow library. Linux Compose is the production target; Windows Docker Desktop is development. No microservice proliferation. |
| ADR-02 | Package boundaries | Target `workflow_engine/` (domain/application/ports/SQLite adapter), `mcp_server/` (FastMCP/OAuth adapter), `controller/` (orchestration), `worker_executor/` (trusted Docker provider), `coder_worker/` (prepare/code/test/publish), and isolated sample `order_service/`. Preserve behavior; keep Git/Docker privileges out of core. Retain FastMCP, Pydantic, pytest and explicit service/repository layers without an unmotivated framework rewrite. |
| ADR-03 | DRY/common | Share pure contracts, path/SHA policy, deadline/time-budget logic and business validation only when semantics match and at least two genuine consumers exist. Document ownership and allowed imports. No giant utils module, cycles, import side effects, network/DB/IO, credentials or Docker capability in shared worker contracts. |
| ADR-04 | Persistence | Keep SQLite3 on a single host, using the same physical Docker-managed Linux-local persistent volume for MCP and Controller. No Windows-host live DB bind mount or shared/network filesystem assumption. Evaluate PostgreSQL only for demonstrated multi-host, HA or contention requirements beyond measured SQLite capacity. |
| ADR-05 | Versioned schema | Small ordered Python/SQL migration runner with `PRAGMA user_version`, deterministic preflight, transactions, integrity and backup/restore tests. CL-11 removes `coder_dispatches` runtime DDL. Reject unknown versions and silent initialization at a wrong path. SQLAlchemy/Alembic requires concrete complexity evidence justifying adoption. |
| ADR-06 | Trusted worker execution | Controller uses a narrow typed internal executor API: job ID, approved image digest, task/workspace ID and bounded parameters. Prefer executor container plus dedicated rootless worker Docker daemon on Linux, subject to security/platform validation. Controller/MCP/Codex have no host-wide daemon access. Generic socket proxy alone is insufficient; privileged DinD is excluded. If validation fails, return to Owner for explicit approval of a minimal trusted host executor with reviewed local IPC. No automatic fallback or privilege broadening. |
| ADR-07 | Workspaces | Executor owns daemon-host-real path/volume mapping and workspace isolation. Controller uses logical workspace IDs, avoiding Windows absolute-path dependence and arbitrary host mount injection. Preserve allowed paths, repository provenance and source snapshots; separate trusted prepare/publish from untrusted code/test. |
| ADR-08 | Operations/secrets | Independent images/entrypoints and dependency-specific packaging; explicit start, health checks, restart, blocking/reconciliation, redacted logs and pinned versions/digests. Separate OAuth, GitHub App and Codex auth scopes. Require safe backup and verified restore. Deploying MCP must not silently enable Controller/dispatch. No `compose down -v` or hot raw SQLite copies. |

Target dependency direction: MCP and Controller depend on workflow application
and ports; application depends on domain and ports; SQLite infrastructure
implements ports and is wired by the composition root. Pure core/shared code
never imports MCP, Controller, Worker, auth transport or Docker. `coder_worker`
does not import workflow DB/application packages; optional `worker_contracts`
contains only proven minimal pure contracts. `order_service` remains independent
with no runtime dependencies.

## Validation gates — plans, not executed spikes

CL-12 records the following required evidence for later separately authorized
implementation/validation tasks. This documentation task does not execute
Docker, live database or deployment drills.

1. **ADR-06 security/platform gate:** compare B2 (executor container + dedicated rootless worker daemon) with B1 (trusted host executor + narrow authenticated local IPC). Prove Linux and Docker Desktop seccomp, UID, mounts, network, pids/CPU/memory restrictions, malicious argument/path rejection, secret/socket isolation and crash stop/reap/cleanup. Socket access must not allow arbitrary container flags or host mounts. Failed feasibility returns to Owner; no privileged DinD or silent fallback.
2. **ADR-04/05 persistence gate:** validate locking, `busy_timeout`, `BEGIN IMMEDIATE`, transactions, WAL and crash recovery with both processes on the same local filesystem. Plan explicit one-shot migration before startup, version/integrity preflight, rollback and isolated restore tests. Use SQLite online backup or coordinated downtime; never raw-copy an active DB. CL-10.1 inventory reports both DBs at schema v1 with zero workflow rows; this is inherited audit evidence, not a fresh inspection or permission to skip backup. Preserve legacy `techlead-review-poc_mcp_state` until separately approved decommission.
3. **ADR-07 portability gate:** prove daemon-host path/volume resolution on Linux and Docker Desktop, source snapshot hygiene, task write allowlists, repository provenance and bounded resources. No unauthorized `.git`, credentials, DB or socket mounts in code/test. Existing linked-worktree/absolute-path requirements need an explicit migration design.
4. **ADR-02/03 architecture gate:** static import-boundary tests, shared path/validation parity and no duplicate security policy. Core must not import FastMCP/auth/Docker/worker; shared packages have no privileged import effects. Worker image must copy only needed packages rather than all `src/`. Preserve SHA, rounds, lease, failure and idempotency behavior.
5. **ADR-08 operations gate:** document and later verify explicit start, health, restart, uncertain-dispatch fail-closed reconciliation, backup/restore/rollback, OAuth/auth and per-stage secret scopes. No automatic redispatch after uncertain effects and no deployment-triggered worker start.

CL-07 regression baseline precedes CL-09, which remains rename-only. Actual MCP,
Controller, SQLite-port/shared-contract extraction and Executor implementation
need separate atomic tasks approved by Owner. Do not combine rename, business
refactor, schema migration and privilege redesign. CL-11.x owns schema migrations;

## Roles, Git and review gate

| Role | Responsibility |
| --- | --- |
| Codex Coder | Read authorized sources; create only allowed docs; validate, commit, ordinary push and create one PR; report evidence. Never approve own work, assign final approval to another agent, merge or start the next task. |
| ChatGPT Tech Lead | Authorize tasks, review acceptance criteria and exact base-to-head diff, verify remote SHA/ancestry through GitHub plugin, record review decision/escalation. |
| Owner | Approve merges, final ADR contents, live-infrastructure decisions and release of subsequent tasks. Tech Lead approval alone is not merge authorization. |

Use one atomic task per dedicated branch/worktree/PR. Keep main clean; record
base SHA before changes, commit focused changes, push normally and verify the
remote head equals the reported full head SHA. Never force-push or merge.

Review follows `docs/review-policy.md`: at most two formal Tech Lead rounds.
Round 1 failure is CHANGES_REQUESTED; fixes may be submitted for round 2.
Round 2 failure is ESCALATED; stop automatic rework and await Tech Lead direction.
Only Tech Lead records APPROVED/escalation. Immediately before approval, Tech
Lead checks the remote branch head equals the reviewed SHA and verifies base
ancestry with the GitHub plugin; repeat before any Owner-authorized merge.
A later commit invalidates approval for the new head and requires review within
the same two-round limit, otherwise escalation. No third formal round.

Each review records task/round, requested effort (`instant`, `medium`, `high`),
verified model/effort evidence or `unverified`, base/head SHA, AC-mapped findings,
test evidence, decision, reviewer identity and timestamp. CL-12.1 has no explicit
requested effort in the source task; report unspecified rather than claiming
verified settings. Missing required verified High evidence stays blocked for
Tech Lead resolution, never silently downgraded.

Stop after PR/handoff for exact-SHA Tech Lead review. Owner approval/merge and
explicit next-task authorization are separate gates, not inferred from kickoff.
