### 1. Objective and boundaries

Enable **Dev**, **QC**, **Independent TL Reviewer** as isolated ephemeral CLI Workers; trusted role/phase and model/effort selection; permitted task-context bootstrap; auditable, bounded execution; and portable adapter/output contracts. **V1 implements Codex CLI + at least one deterministic fake adapter only.** Claude Code CLI and OpenCode CLI are future adapter tasks; providers are independent of role and runtime.

Keep existing **trusted host Controller → Docker CLI → Worker**, Phase 3.1 Prepare → Code → Test → Publish, the nine MCP tool names/contracts/auth, Worker-only GitHub App auth and scoped Draft PR behavior. No Executor/Podman migration, automatic PR merge, new DB schema, new planning/Owner registry, V1-03 exact-HEAD Controller CI automation, V1-10 QC verdict store/revalidation, active credential/DB edits or production deployment. These remain their separately approved work/gates. No untrusted role obtains GitHub App PEM, live WFC SQLite, host engine socket or Owner authority.

### 2. Acceptance criteria (normative)

**AC-01 — Config and effective model/effort (unchanged except portable runtime binding).**
Trusted role mode recognizes canonical `dev`, `qc`, `tl-reviewer`; requires `DEV_MODEL`, `DEV_EFFORT`, `QC_MODEL`, `QC_EFFORT`, `TL_REVIEWER_MODEL`, `TL_REVIEWER_EFFORT`. Validate **all three pairs at trusted startup**, even inactive roles, against an operator-pinned, versioned, CLI/provider-qualified support catalog. Missing/blank/whitespace-padded/noncanonical, unknown or unsupported pairs, conflicting trusted sources or attempts at untrusted overrides fail **before role spawn**; no silent default/provider/CLI/effort fallback. Explicit legacy mode alone preserves prior single-model Phase 3.1 behavior. Record requested and **independently verified effective** settings or an explicit `UNVERIFIED` observation that cannot pass required online-smoke gates. A CLI or model-generated text claim is never effective-setting attestation.

**AC-02 — Trusted role/phase, permissions and phase-specific authority (PG1-01, PG1-02).**
The Controller selects one of six profiles: `dev/code`, `qc/pre-dev`, `qc/post-code`, `tl-reviewer/plan`, `tl-reviewer/code`, `tl-reviewer/qc`. A request, prompt, MTP, PR, tool output or model response cannot choose/escalate a role, permission, credential or approval.

Use **two non-interchangeable trusted authorization classes**, both externally issued and independently verified at preflight:
- `DRAFT_PLANNING`: for **`qc/pre-dev` and `tl-reviewer/plan` only while Owner Gate is Pending**. Carries `task_id`, immutable draft Plan/MTP Git revision or content digest(s), authorized role/phase, distinct QC-author/reviewer identities, scoped input manifest, permitted MTP-only author output or immutable reviewer verdict sink, issuance/attempt identity. It **does not** assert a frozen/Owner-approved package; a planning reviewer is read-only even if a QC author may edit the proposed MTP in their own separate task workspace. A positive launch with valid draft authorization must succeed *without* a forged Owner-approval fixture.
- `APPROVED_EXECUTION`: required for `dev/code`, `qc/post-code`, `tl-reviewer/code`, `tl-reviewer/qc`. Carries an **Owner-approved immutable Planning Package identity/hash** plus exact task/base/expected HEAD/snapshot, current gate-specific attestation and scoped capabilities. Dev requires package approval; code review requires current reviewed HEAD and applicable CI; post-code QC requires exact reviewed source + frozen MTP and applicable code/CI gates; TL QC evidence review requires authenticated, immutable QC evidence attempt. A gate that is not implemented automatically must be checked by a **separately authorized trusted operator**, never inferred from agent claims. Do not confuse these *authorized inputs* with implementing the future gate registries in V1-02.

A `DRAFT_PLANNING` token/manifest **must be rejected** for Dev/post-code/TL code or QC phases; reject replay to a different task/revision/role/output, wrong phase or forged Owner approval with zero launch. Conversely, no Owner approval is demanded for the two valid planning profiles. Unknown authorization kind, stale revision, conflicting role/issuer or missing required gates fails closed.

Role/phase least-privilege matrix:

| Profile | Allowed input | Allowed output only | Denied examples |
| --- | --- | --- | --- |
| `qc/pre-dev` | Version-pinned draft Plan/AC/templates and conventions | Proposed MTP in QC worktree, controlled handoff | Runtime source edits, credentials, self-approval, PR merge |
| `tl-reviewer/plan` | Exact proposed Plan/AC/MTP revision | Separate read-only review record keyed to reviewed input | Editing Plan/MTP, impersonating QC/Owner |
| `dev/code` | Owner-approved package, scoped source/tests, relevant architecture | Allowlisted source/tests in disposable snapshot only | GitHub writes, out-of-allowlist edits, QC/Owner verdict |
| `qc/post-code` | Frozen MTP, reviewed snapshot, read-only gate evidence | Disposable harness/evidence + separate MTP execution report | Change source or frozen MTP, review verdict |
| `tl-reviewer/code` | Exact code diff/HEAD/CI and approved package | Controlled code-review output | Edit code, push/merge, Owner approval |
| `tl-reviewer/qc` | QC execution evidence/frozen plan and source identity | Controlled QC-evidence-review output | Edit QC report/harness, Owner approval |

Across every role, enforce actual mounts, tools, subprocess, network and filesystem restrictions **outside prompts**. Synthetic positive allow and negative deny probes test both role-pair and role-phase separation, no cross-attempt private cache/session reuse and no GitHub/WFC/host engine privilege.

**AC-03 — Pinned image, attempt ownership and lifecycle (PG1-04).**
Prefer **one immutable image digest and pinned Codex CLI identity** for all three ephemeral Codex roles, no always-on three-agent services. An extra image is allowed only after separate **Owner-documented exception** citing reproducible incompatibility, exact digests and separate cleanup verification. Each Docker create/run/stop/reap attempt must have a unique trusted `attempt_id` and independently verifiable owned identity (engine endpoint/context, image digest, task/dispatch ID, nonce, authenticated label set and persisted actual container ID once known). **Container name alone, one empty list, or agent output is not ownership proof.**

Define **smoke runtime budget: 180 seconds per role** and **cleanup/reconciliation grace target: 60 seconds after timeout/failure**, separately measured. Grace expiration is **BLOCKED**, not permission to release ownership or replay. Probe **delayed Docker create completion after the caller timed out**, late arrival after an empty inventory, missing/colliding labels and wrong-engine/unowned container: never clean up an unverified asset; do not replay/publish/advance task or release the dispatch fence until a trusted operator proves no late command or write principal can still affect the attempt and exact owned resources are settled. No new global Controller/Executor recovery platform is mandated by this AC; inability to implement safe fencing in V1-02 is an **escalated design/Owner decision**, never a silent exception.

Deterministic fault injection is mandatory; **one authorized isolated real-Docker lifecycle check with owned ID/late-effect-or-verified-quiescence evidence** is a DoD prerequisite. Mere CLI process exit or mocked cleanup is insufficient for that check. No active workload is used.

**AC-04 — Bounded headless smoke, auth separation and evidence (PG1-02/03).**
Once **separately authorized by Owner/operator**, execute one distinct online headless invocation for each Dev/QC/TL Reviewer, fresh disposable workspace, chosen phase recorded, one attempt/role with no automatic retry, **≤180 s execution** and **≤65,536 bytes retained sanitized output** per role; verify only explicitly approved provider egress and forbid redirects elsewhere. Never paste auth, PEM or live tokens into prompts, workspace, chat, PR or reports.

**Same-role credential boundary MUST be tested independently:** provide a **synthetic authentication canary through the same launch/mount/broker/UID/namespace pattern** intended for the Codex CLI. Positive: the trusted CLI/launcher can acquire/use the test credential for the authorized provider operation. Negative: agent-controlled tool commands, shells/subprocesses, workspace/file reads, inherited environment and all captured outputs/evidence **cannot read or export the credential bytes** even from their *own* role; redirects to denied egress remain blocked. Check actual observed OS/container policy and launch-time mounts, not an instruction that says 'do not read'. Baseline code mounts the Codex home volume into the Code stage: this is a **potential exposure to prove or remediate, not a demonstrated protection**. If the pinned CLI and available isolation cannot meet both positive and negative controls, mark **BLOCKED** and **do not run with real credentials**; obtain explicit Owner scope/architecture change. Neither redaction nor denying other roles' auth substitutes for same-role read denial.

For actual online smoke, independently capture invocation ID, exact source snapshot/HEAD, requested settings and **observed effective model/effort from pinned CLI/runtime telemetry**, image/CLI identity, bounded exit/usage where available, sanitization proof and cleanup receipt. Missing verified effective telemetry, provider egress evidence, redaction or cleanup ⇒ `BLOCKED`. The model's reply/marker or agent-authored JSON alone cannot prove provider selection. If the pinned CLI does not expose effective effort observably at the execution boundary, stop rather than claiming PASS; owner-approved alternate attestation design is needed.

**AC-05 — Provenance and baseline compatibility (PG1-01/05/06).**
Trusted launch verifies the exact **authorization kind**, role/phase, task, immutable draft revision **or** approved package hash (as appropriate), MTP identity, base/expected HEAD and snapshot digest, changed-path allowlist and relevant gate evidence. Recheck immediately before dispatch and handoff. Missing/stale/malformed/mismatched/forged inputs or unauthorized files ⇒ zero launch or stop `BLOCKED`; no self-hashed blob can override trusted authorization. Keep the **trusted launch preflight** distinct from **manual operator gate verification** for V1-03 code CI, independent TL review, Owner merge and post-QC changed-HEAD revalidation; do not implement or pretend these future gates already exist.

Deterministic offline regression must include original Phase 3.1 stage order, no source mutation during Test, Worker-only scoped GitHub App, all 9 MCP names/response/auth invariants and **explicit legacy review-state sequences** using isolated SQLite: `CHANGES_REQUESTED → APPROVED` on the second formal code-review submission; first+second formal failures → `ESCALATED`; stale SHA and third submission denied; handoff after `APPROVED` denied with **unchanged counters, immutable review/finding history and state**. The manual operator gate negative matrix includes: CI PASS but missing TL verdict; verdict mismatched task/HEAD/package or self-reported; stale/pending/ambiguous CI; and same-SHA failed-then-passed CI requiring Owner acknowledgment. Historical WFC code verdict is **not** a planning/QC verdict registry. No live PEM ACL, systemd continuity or real App writes are tested in V1-02; record these N/A, not PASS.

**AC-06 — Portable WorkerBundle, runtime adapters and context bootstrap (PG1-03/06).**
Four dimensions stay independent: `role+phase`, `runtime_id`, `provider_id/model_id/reasoning_profile`, and allowed task context. Trusted `RolePolicyResolver` and `TaskContextBuilder` compile canonical `AGENTS.md`, `docs/INDEX.md` (router), `docs/roles/{role}.md`, only selected versioned architecture/conventions and Plan/AC/MTP/evidence into a bounded, content-hash-pinned **WorkerBundle**. Unapproved user/home/project auto rules (`CLAUDE.md`, stray `AGENTS.md`), hooks, skills, plugins and MCP tool configs must be disabled or independently traced and rejected if they expand authority. An ordinary prompt payload is **not necessarily a system-priority message**; record the actual pinned CLI delivery mode and precedence.

For v1, use **`WorkerBundle.schema_version = 1`** with fields:
`{schema_version, task_id, authorization:{kind,issuer_ref,revision_hash|approved_package_hash}, role, phase, runtime_id, provider_id, model_id, reasoning_profile, policy_sha256, source_manifest:[{path,git_revision,content_sha256,trust_class,visibility}], context_sha256, base_sha, expected_head_sha, snapshot_sha256, allowed_read_paths, allowed_write_paths, output_channel, attempt_id, limits}`.
Interpret `revision_hash` **only for DRAFT_PLANNING** and `approved_package_hash` **only for APPROVED_EXECUTION**; strict types, required fields per phase, canonical lowercase 64-hex digests, unknown/duplicate/unsupported versions and unexpected capability fields fail closed. Canonical hash input is UTF-8 JSON with sorted keys, no insignificant whitespace and no NaN/Infinity, as independently reproduced by the verifier; a self-declared hash is never authorization. **Maximum serialized WorkerBundle: 524,288 bytes; maximum one selected document: 131,072 bytes** (limits include UTF-8 multibyte). Required context above limits is **BLOCKED**, never silently truncated; optional lower-trust evidence may be omitted only under a documented deterministic role/phase selection policy and manifest.

**Time-of-check/time-of-use:** after preflight, independently verify source bytes/source digest, manifest, role/policy and snapshot again **immediately before starting the CLI**; mutate a selected document or snapshot between preflight/launch in a deterministic negative test to prove **zero launch**. Recheck dynamic HEAD/diff/CI/findings/QC at every dispatch and handoff. Static document content may be memoized only by `content_sha256 + policy_sha256 + role + phase + visibility`; never cache a combined dynamic authorization or another role's private session.

`AgentRuntimeAdapter` interface: `validate(config, capabilities)`, `prepare(bundle)`, `execute(invocation)`, `normalize(raw)`. `RuntimeRegistry` validates pinned adapter/CLI/image/provider capability combinations. V1 delivers one **actual Codex CLI adapter** and one **fake adapter** with a different input/delivery format; unsupported role/provider/model/effort, unregistered runtime and implicit fallback all fail before spawn. Fake substitution must not alter package/task identity, allowed capabilities or gate results.

For v1, use **`WorkerResult.schema_version = 1`** with `{schema_version, attempt_id, task_id, role, phase, runtime_id, provider_id, requested_model, requested_reasoning, observed_model, observed_reasoning, telemetry_status, source_head_sha, snapshot_sha256, output_manifest_sha256, changed_paths, process_exit_code, timeout, sanitized_log_refs, findings, process_status}`. `telemetry_status` is `VERIFIED|UNVERIFIED|UNAVAILABLE`; `process_status` is `COMPLETED|FAILED|BLOCKED`, **not a CI, QC, TL or Owner verdict**. Reject malformed/extra fields, wrong attempt/task/phase/HEAD, unsupported version, unverifiable output digest or unsafe side effects. Model-supplied `SUCCESS` cannot satisfy independent gate verification.

**Pinned Codex v1 demonstration/probe:** current Dockerfile pins Codex CLI **0.161.0** at `docker/coder.Dockerfile` (version may change only by separate approved path scope). Offline: using controlled prepared input and OS/CLI/file-access probe, capture actual bytes delivered through stdin/config, instruction auto-load precedence with canary project/home rules, and exact argv/config + sandbox restrictions; no real provider login required. Online: separately authorized provider invocation produces independent telemetry bound to **same invocation/attempt ID**; record observed effective settings and explicitly distinguish launcher observations, CLI metadata, model text and missing telemetry. If the pinned CLI lacks a verifiable route, **BLOCKED**, not a claim that another CLI mechanism 'probably works'. Claude Code/OpenCode CLI *real adapters* are not required, launched or given credentials in V1.

### 4. Verification plan and definition of done

1. **PRE-DEV:** TL Planner versions AC-01–06/DoD + path scope and resolves PG1-01..06. Codex QC *independently* revises MTP 0.3 with positive/negative/edge tests anchored to this Plan; all statuses `NOT RUN`. Independent Codex TL Reviewer conducts **formal Planning Review round 2/2** on exact Plan commit + MTP HEAD, citing each PG1 resolution. Changed Plan/MTP bytes after verdict invalidate that verdict for final approval; exhausted second failure ⇒ **ESCALATED to Owner**, not a silent round 3.
2. **Trusted freeze/Owner Gate:** trusted operator computes raw UTF-8 file SHA-256 for immutable Plan and MTP, captures both Git SHAs/AC/test IDs/policy/source allowlists into an external immutable manifest, obtains one explicit Owner Planning Package approval of its digest. `DRAFT_PLANNING` authorization may exist before this gate; `APPROVED_EXECUTION` may not.
3. **Dev only after Owner approval:** implement bounded adapter+role+context/auth protection with deterministic offline tests. Preserve Phase 3.1 and nine MCP tools; no changed-path violation, unauthorized privilege or silent fallback.
4. **CI and code review:** exact-current-HEAD named GitHub Actions PASS plus independent TL code review; record CI run/check identity, current diff and package. No CI result alone clears MTP.
5. **POST-CODE QC:** execute every approved required case against exact source snapshot and record independent evidence; three online smokes and one real isolated Docker lifecycle check require separately recorded Owner/operator **execution** authorization and the credential/provider restrictions in AC-03/04. Any unsafe credential boundary, unknown cleanup, missing telemetry, stale SHA, required `NOT RUN` or absent evidence remains **BLOCKED**, no invented PASS.
6. **QC evidence and Owner merge:** independent TL accepts QC assertions/evidence through the correct separate gate; Owner alone authorizes merge of exact-HEAD PR; Controller reconciles verified GitHub merge SHA. Preserve original retry/round budgets; never use legacy WFC code review to create planning or QC verdicts.
