**Ordering established from code:** Controller acquires persistent `ACTIVE` dispatch slot → runs Prepare/Code/Test/Publish → Publish may commit/push/create or update a Draft PR on GitHub **before** writing `result.json` → Controller validates local result → `WorkflowService.register_task_handoff()` commits a separate transaction → `DispatchLedger.finish()` sets `DONE` and releases slot in another transaction. `run_once` attempts to mark `BLOCKED` on exception; abrupt process death may leave `ACTIVE`. The persisted dispatch key is `(task_id, round_number, input_sha)`; same-key automatic re-dispatch is suppressed. Neither ledger nor local handoff alone proves the current remote GitHub outcome.

## Uncertain-outcome matrix — evidence to reconcile (NOT a recovery command recipe)

**Universal safety rule:** Stop/pause new Controller dispatch before inspection. Identify the **correct physical workflow SQLite DB and Docker endpoint/context**, then verify that the named dispatch row still holds the `slot=1` lease (status `ACTIVE` or `BLOCKED`), its task/round/input SHA, and all possible containers belonging to that dispatch. **Never infer ownership from the generated container name alone:** `CoderRuntime.stop()` matches an exact derived name and checks that no container with that name remains, but it does **not** validate a container label or immutable container ID. Verify provenance/identity and task association independently before any destructive action. A killed/disconnected Docker CLI process does not prove that an in-flight create request was aborted by the daemon; a late create is **UNKNOWN** until the actual engine/container state is reconciled. Preserve the slot if evidence is missing, contradictory or still changing. Verify exact remote branch head, PR head, author and handoff/DB state; never automatically replay a potentially published job.

| Crash/uncertain boundary | Possible local observation | Remote effect that **may** already exist | Evidence / decision boundary |
| --- | --- | --- | --- |
| After `claim`, before or during Docker create | Dispatch still `ACTIVE` after abrupt death or `BLOCKED` if caught; slot=1 | No GitHub change expected this early, **but do not infer worker state from ledger alone** | Check exact dispatch ID/container names and task SHA, and reconcile any remaining worker before declaring stop; not an automatic retry |
| During Prepare, Code or Test, before Publish | `ACTIVE`/`BLOCKED`, no accepted `result.json` | Normally no publish yet; actual stage reached is uncertain after disconnect | Confirm stage/container lifecycle and artifacts; preserve slot on unknown status |
| During Git push or after push, **no existing Draft PR** | `ACTIVE`/`BLOCKED`; result missing | Remote branch may have moved even when no PR exists; push response may be lost | Check exact branch SHA/ancestry, App attribution, whether a PR was created after the last observation, and local handoff before considering any authorized intervention; **do not replay publish** |
| During Git push, **Draft PR already exists** | `ACTIVE`/`BLOCKED`; result missing; PR body may still show an old handoff SHA | An existing Draft PR tracks its branch: **PR head may already point at the newly pushed commit while PR body still describes the previous SHA** (PATCH follows push) | Inspect **branch head SHA, PR head SHA, PR author/base/draft status and PR body/handoff SHA** separately. A matching branch/PR head does not prove that the body/evidence update succeeded; keep the job blocked until reconciled |
| During or after **PR POST/PATCH**, before `result.json` | `ACTIVE`/`BLOCKED`; result missing | POST may have created a new bot Draft PR, or PATCH may have changed the body of an existing Draft PR **even when HTTP response was lost** | Query latest branch SHA, PR head SHA, draft/owner/base and PR body/handoff text independently; check for unexpected duplicate PRs and do not infer request failure from timeout or issue another POST/PATCH automatically |
| `result.json` present, before or during local handoff | Dispatch may still `ACTIVE`/`BLOCKED`, WFC task may remain `AWAITING_HANDOFF`/`CHANGES_REQUESTED` | Remote branch/PR may already be complete | Validate file provenance and exact SHA/PR against GitHub, then inspect WFC state; local result is worker-reported, not remote verification |
| After handoff commit, before dispatch `DONE` commit | WFC can be `READY_IN_REVIEW` while dispatch is still `ACTIVE`/`BLOCKED` | Remote branch/PR may already exist | Check **both** SQLite task/handoff and dispatch records plus exact GitHub SHA; no second publish solely because ledger says not DONE |

**What the built-in acknowledgement does and does NOT do:** The existing operator CLI `python -m my_wfc.controller CONFIG --acknowledge DISPATCH_ID --reconciled` (see [Phase 3.1 runbook](../phase-3.1.md)) obtains the process lock for the configured DB, requires an operator to **assert** prior reconciliation, then runs `CoderRuntime.stop()` **by derived exact container names** before `DispatchLedger.acknowledge()` checks a matching active slot and releases it. **The CLI does not itself prove that the dispatch row/DB was the intended one before cleanup, does not verify container labels/IDs or ownership, does not rule out an in-flight daemon create request, and does not verify GitHub branch/PR/handoff correctness.** A wrong endpoint or incomplete engine observation can leave uncertainty. An authorized operator must confirm the correct DB/dispatch identity and Docker endpoint, account for all owned/late-created containers and independently reconcile GitHub + local WFC state **before** invoking it. If any precondition is uncertain, retain `ACTIVE`/`BLOCKED` and escalate; do not run acknowledge. Do not run this command from an agent or on production without separate Owner/operator authorization and recorded evidence. Acknowledgement **does not clear the original unique idempotency key** or automatically rerun the same job. No review round is consumed by an operational failure.

## TARGET contract (not CURRENT code)

The [merged CL-12 architecture ADR](../adr/CL-12-architecture.md) selects a separate unprivileged Linux-host Trusted Executor using local Rootless Podman CLI, with authenticated bounded Controller→Executor IPC, durable job identity, isolated Prepare/Code/Test/Publish stage containers and fail-closed unknown outcomes. [Executor security ADR §3](../adr/CL-12-executor-security.md) sketches `submit/status/stop/reconcile` and replay semantics. **These are design requirements, not implemented APIs.** The security ADR's earlier `§8 Current gate` paragraph calls PR #12/#13 Draft; that paragraph is a **dated pre-merge record**, superseded by the verified merge statuses in the consolidated ADR. It remains unchanged in this PR because `CL-12-executor-security.md` is outside the DOC-02 path allowlist.
